# AGENTS.md

Guidance for AI coding agents (Claude Code, Codex, Gemini CLI, Cursor, Copilot, etc.) working in this repository. `CLAUDE.md` imports this file, so edit here, not there.

## What this repo is

Ansible automation for a 4-node Turing Pi 2 home cluster (Ubuntu boards, and the Turing Pi's BMC driven with the `tpi` CLI). The installation's own values are its site layer: the nodes and their addresses in `inventory/hosts.ini`, their host keys in `inventory/known_hosts`, everything else in `inventory/group_vars/all/site.yml` (see "Site layer and public copy"). Docs, comments and examples use the example site of `publish/example/` instead (boards `node1`..`node4` under `home.arpa`, BMC 192.168.1.31, `data.example.org`): read the real names from the site layer. One inventory and one `ansible.cfg` at the root serve two kinds of code:

- `cluster/` — whole-cluster lifecycle that knows nothing about workloads: BMC power on/off, graceful shutdown, rolling reboot, package updates, OS baseline.
- `subsystems/<name>/` — one directory per complex subsystem: `ceph` (upstream containerised Ceph deployed with **cephadm**, not MicroCeph, with RGW/S3, STS, HA ingress, CephFS, monitoring, benchmarks) `k3s` (HA k3s with ceph-csi StorageClasses on that Ceph), and `dataplatform` (Trino and Spark on k3s, installed by Argo CD from `subsystems/dataplatform/gitops`, with Keycloak, a Samba Active Directory domain as the only source of its users and groups, OpenBao and an OpenTelemetry/VictoriaMetrics/VictoriaLogs/Grafana stack, with Vector feeding the Stackable product logs into OpenTelemetry; every data access goes through Ceph STS roles).

There is no build or unit-test tooling; everything runs against live hosts. The offline checks are `make syntax-check` (`ansible-playbook --syntax-check` over every playbook), `make lint` (ansible-lint, `production` profile, configured in `.ansible-lint`; it installs `requirements.yml` for its run), `make configure-check` (every file rendered from the site's settings is current) and `make site-check` (no site value written anywhere else); keep them clean.

## Commands

Run everything from the repository root; `ansible.cfg` there points at `inventory/hosts.ini` and sets `become`.

```bash
make help                                   # every command, with descriptions and examples
make cluster-status | cluster-power-on | cluster-shutdown | cluster-reboot | cluster-update | cluster-baseline
make ceph-install | ceph-status | ceph-osds | ceph-s3 ...   # ceph-<playbook> -> subsystems/ceph/<playbook>.yml
make k3s-install | k3s-status | k3s-storage-test | k3s-kubeconfig
make dataplatform-install | dataplatform-status | dataplatform-sync | dataplatform-iam | dataplatform-smoke-test
make dataplatform-s3-login ARGS="-g data-engineers"   # files/dp-s3-login.sh: Keycloak device login -> STS keys in .secrets/sso-<user>.env
make dataplatform-directory ARGS="user list"          # files/dp-directory.sh: users and groups, in the directory (Samba AD); also user add|passwd|disable|remove, group add|join|leave
make dataplatform-render                    # builds every Argo CD Application offline (kubectl kustomize, helm template)
make ceph-s3-user ARGS="-e uid=alice"          # also: ceph-s3-users, ceph-s3-user-remove ARGS="-e uid=alice [-e purge_data=true]"
make ceph-sts-role ARGS="-e role_name=r -e trusted_uid=alice"
make ceph-remove ARGS="-e remove_confirm=yes"                # destructive, 10 s countdown
ansible-playbook subsystems/ceph/osds.yml --limit node4      # single step, single host
ansible-playbook cluster/reboot.yml -e target=node1          # single node
make configure                              # render the files that carry the site's settings (inventory/group_vars/all/site.yml)
make syntax-check
make lint
make configure-check site-check
make publish-check | publish | publish-push   # the public copy on GitHub: the example site instead of this one (publish/)
```

Playbooks that need input take it via `-e` (`uid`, `role_name`, `trusted_uid`, `target`, ...) and `assert` on it; none use `vars_prompt`.

`make help` is generated from the Makefile: every user-facing playbook has an explicit target with a `## description` on the target line, optional `##> example` lines after the recipe, and `##@ Section` headings. When adding or renaming a user-facing playbook, add or update its target there; destructive targets use `$(call countdown,...)`. The `cluster-%` / `ceph-%` / `k3s-%` pattern rules only remain as a fallback for internal playbooks. The README is written for users with little Ansible/make knowledge; keep it that way (task-oriented, copy-paste commands, troubleshooting table).

## Architecture and conventions

### Settings: one place (`inventory/group_vars/all/site.yml`)

- Every value that belongs to this installation rather than to the software is a flat `site_*` key of `inventory/group_vars/all/site.yml`: the cluster name, the LAN domain and network, the S3 VIP, the k3s API VIP and pod CIDR, the DNS zone, the platform domain, the S3 host, the ACME email, the Git repository, revision and host keys, the Keycloak realm and the three groups (admin, engineer, analyst), the directory's AD domain and its NetBIOS name, the S3 region, the bucket, the backup bucket, the RGW account id and name, the storage classes. Plain YAML, no Jinja (plain Python reads it). The node list and each node's `node_ip` are `hosts.ini`'s. Nothing else may hold one of these values.
- Every other variable derives from them and keeps its own name (`dataplatform_domain: "{{ site_platform_domain }}"`, `ceph_rgw_acme_domain: "{{ site_s3_host }}"`, ...): use the subsystem's variable, never `site_*` directly, outside the group_vars and the templates.
- A file the cluster or a script reads (the gitops tree, `files/site.env`, the Meta Catalog model and lakehouses) that carries a site value is rendered from a template next to it, `<file>.in` -> `<file>`, by `make configure` (`subsystems/dataplatform/configure.yml`, role `dataplatform_configure`: the template module over every `*.in` under the data platform's `gitops/`, `files/` and `metacatalog/`, on the control node, as the first k3s server so every derived variable is there, `secrets_dir` pointing nowhere). The outputs are committed: Argo CD deploys what is in Git. **Never edit a file that has a `.in` sibling**: edit the template (or `site.yml`), run `make configure`, commit both. CI (job `ansible`) renders and fails on any difference; `make dataplatform-preflight` fails on a stale file.
- Template syntax: Jinja with delimiters found nowhere else in the tree, `<%= expr %>`, `<% for/if %>`, `<%# comment %>`, `trim_blocks` and `lstrip_blocks`; Helm's and ESO's `{{ }}`, the shells' `${...}` and `[[ ]]` stay plain text. Lists come from loops (the network policies' per-node pod addresses from `site_k3s_cluster_cidr` and the node count, the Ceph managers' scrape targets from `node_ip`), regexes from `regex_escape`, JSON lists from `to_json`.
- `make site-check` (`files/site_check.py`, CI) fails when a site value, or its regex-escaped form, or the LAN's or pod network's prefix, appears in any tracked file but `site.yml`, `hosts.ini`, `inventory/known_hosts`, the rendered outputs, `*.md`, `files/tests/` and `publish/example/`; comments included (write `<node>.<cluster_domain>`, "the admin group"). Generic words are not searched (the revision, the bucket and account name, the storage classes, the directory's NetBIOS name).
- Install-time values (marked in `site.yml`): changing them on a running platform is a migration, not a re-run: the realm (Ceph trusts its keys, the roles its tokens), the AD domain and its NetBIOS name (the directory is provisioned under them), the RGW account id (every role ARN), the bucket (the data), the pod CIDR, the cluster name (metric series), the platform domain (the label keys `<domain>/user` and `<domain>/managed-by`, iam-sync's RoleBindings).
- The user-side scripts read `files/site.env` (rendered: `: "${VAR:=value}"` lines, sourced by `lib-keycloak.sh`; the environment wins): `KEYCLOAK_ISSUER`, `METACATALOG_URL`, `TRINO_URL`, `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `ROLE_ARN_PREFIX`, `USER_ROLE_PREFIX`, `GROUP_ROLE_PREFIX`, `LABEL_DOMAIN`. Python programs in the gitops tree take their site values from env their manifests set, with no defaults.

### Site layer and public copy (`publish/`)

- The site layer is this installation's own: `inventory/hosts.ini` (nodes, `node_ip`, the BMC's address), `inventory/known_hosts` (their SSH host keys), `inventory/group_vars/all/site.yml`, and the files `make configure` renders from them. It lives in the deployment repository (GitLab, which Argo CD reads) and nowhere else. Everything else (code, templates, docs, comments, Makefile examples) is published as it is, so it never names the real site: docs and examples use the example site of `publish/example/` (`site.yml`, `hosts.ini`, `known_hosts`: boards `node1`..`node4` under `home.arpa`, LAN 192.168.1.0/24, `example.org`, the Git repository on github.com with GitHub's host keys). Never write a real node name, address, domain or e-mail outside the site layer; never edit the real site files for the publication.
- `publish/publish.py` makes the public copy: `git archive HEAD` (it refuses uncommitted changes) into a separate Git repository, `../<this folder>-github` (never inside this one; it empties only a repository it created, marked `.git/publish-copy`), `publish/example/` copied over the site layer, `make configure` run there. Then the checks: none of the real site's values that differ from the example's (every `site.yml` value, regex-escaped and URL-encoded, the LAN prefix, the zone's and the cluster's distinctive labels, the Git server and its host keys, every inventory host name, address and `known_hosts` key, the e-mail addresses of this repository's commits, the private remote, the home directory), real node names as words (a name that is also an identifier passes where code uses it as one: `CODE_WORD`), no `.secrets/`-like path, the copy's own `site_check.py`, `make syntax-check` with the example inventory, gitleaks (binary or Docker image pinned by digest). The real site files and `git status` are compared before and after. `make publish-check` does it in a temporary directory (CI job `ansible`, `--no-gitleaks --no-syntax`); `make publish` commits in the copy, authored with the GitHub account's noreply address (`gh api user`), one commit per publication (the private history is never published); `make publish-push` checks the copy's history (authors, gitleaks `git`), creates the public repository with `gh repo create` the first time, and pushes. Pushing is the user's decision.
- A new `site_*` key goes into `publish/example/site.yml` too, with an example value (the copy's `make configure` asserts its shape). The example `known_hosts` is empty: README setup step 2 has strangers fill it with `ssh-keyscan`.

### Inventory (`inventory/hosts.ini`, `inventory/group_vars/`)

- `[bmc]` is BusyBox without Python: use the `raw` module only, `ansible_become=false`. `turingpi_slot` on each node maps it to a BMC slot.
- `[nodes]` are the four boards. Ceph groups `ceph_mons`, `ceph_mgrs`, `ceph_mdss`, `ceph_osds`, `ceph_rgws`, `ceph_ingress` (haproxy + keepalived for the S3 VIP), `ceph_monitoring` (union `ceph`). `ceph_hosts` also removes labels of hosts that left a group, so moving a host between groups moves its services. The cluster is self-contained: there are no hosts outside the four boards.
- **Inventory hostnames must be each node's hostname, short or FQDN** (the boards report `<node>.<cluster_domain>`). `node_ip` is each node's LAN address (`preflight.yml` asserts it is the node's default IPv4). cephadm registers hosts under the name the node reports (`ansible_facts['nodename']`), so playbooks never rename a node; `ceph_preflight` and `cluster/baseline.yml` only assert it.
- Subsystem settings live in `inventory/group_vars/<subsystem>.yml` (or `<subsystem>/*.yml` when split by concern, as Ceph's), applied by group membership. Because they are group vars, plays that need them must target a host in that group (never `localhost`); delegate to `localhost` from such a play instead.
- Generated secrets (dashboard and Grafana passwords, STS key, S3 keys) are created with `lookup('password', secrets_dir ~ ...)` on the control node and stored in `.secrets/` (git-ignored). Never hard-code them.

### Hook contract between `cluster/` and subsystems

| Hook in `subsystems/<name>/` | Kind | Called by |
|---|---|---|
| `pre-shutdown.yml` | playbook | `cluster/shutdown.yml` before halting the OS, whole-cluster shutdown only (each play ends at once unless the localhost fact `shutdown_whole` is true) |
| `post-startup.yml` | playbook | `cluster/power-on.yml` after SSH is back, whole-cluster power-on only (localhost fact `power_on_whole`); must also undo what a single-node shutdown left (maintenance mode, cordon) |
| `hooks/rolling-start.yml` | task file | `cluster/rolling-reboot.yml` once, before the first node: fail unless the subsystem is healthy; may append inventory names to the localhost facts `rolling_first` / `rolling_last` |
| `hooks/node-enter.yml` | task file | `cluster/tasks/node-enter.yml` per node (`serial: 1`, `any_errors_fatal`): before a reboot, and before a single-node shutdown |
| `hooks/node-exit.yml` | task file | `cluster/tasks/node-exit.yml` per node: after a reboot, after a single-node power-on, and to undo failed enter hooks; returns only once the subsystem is fully healthy again |
| `hooks/rolling-end.yml` | task file | `cluster/rolling-reboot.yml` once, after the last node: show the subsystem's state |

k3s depends on Ceph, so its hooks run first on the way down (drain / stop before Ceph maintenance / quiesce) and last on the way up; the data platform runs on k3s, so its hooks run before k3s's on the way down and after them on the way up. The data platform has no `pre-shutdown.yml`: a whole-cluster shutdown stops k3s, which stops its pods; it has `post-startup.yml` and the four task-file hooks. Hooks must tolerate an absent subsystem (the Ceph hooks probe `/etc/ceph/ceph.conf` on the admin host, the data platform hooks the `argocd` namespace and the Keycloak resource; `failed_when: false` on the rest), but an installed subsystem whose control plane cannot be reached is an error, not "absent": the k3s and data platform node hooks include `subsystems/k3s/hooks/pick-server.yml`, which sets `k3s_maint_installed`, `k3s_maint_server` (another server whose API answers) and `k3s_maint_member`, and fails when k3s is installed but no server answers (a node must never go down undrained). `cluster/reboot.yml` and `cluster/update.yml` only choose the nodes (localhost fact `rolling_candidates`) and import `cluster/rolling-reboot.yml`; `cluster/shutdown.yml` and `cluster/power-on.yml` use the per-node task files for a subset of the nodes and the pre-shutdown / post-startup playbooks for the whole cluster. Waits that can take minutes loop on the host in one shell task, so no `FAILED - RETRYING` lines are printed. A play that may run against a node that is off starts with `include_tasks: cluster/tasks/ssh-probe.yml` (probe from the control node, `end_host` when down). A new subsystem adds its imports to `cluster/shutdown.yml`, `cluster/power-on.yml`, `cluster/tasks/node-enter.yml`, `cluster/tasks/node-exit.yml` and a `<name>-%` rule to the Makefile.

### Subsystem layout (reference: `subsystems/ceph/`)

- Playbooks sit at the top of the subsystem directory so that `roles/` next to them is found without any `roles_path` configuration; `roles/` at the repository root (`roles_path` in `ansible.cfg`) holds what subsystems share: `acme_lego` (lego + GoDaddy DNS-01, renewal timer, a caller-provided deploy hook; used by `ceph_acme` and `dataplatform_cert`). `install.yml` is only a chain of `import_playbook` over the step playbooks, ending with `cephfs-mount.yml`; every step is independently re-runnable.
- Roles: `ceph_preflight` (packages, cephadm binary), `ceph_bootstrap` (`cephadm bootstrap` on `ceph_mons[0]`), `ceph_hosts` (`ceph orch host add` + labels from `ceph_host_labels`), `ceph_config` (compare-and-set helper for `ceph config`, sets fact `ceph_config_changed`; an entry with `secret: true` is assimilated from a root-only file instead of the command line), `ceph_services` (mon/mgr/crash spec), `ceph_osds`, `ceph_ingress_image` (per ingress host: keepalived image, `ip_nonlocal_bind` sysctl), `ceph_acme` (public A records and the ingress deploy hook around the shared `acme_lego` role; `s3-cert.yml`), `ceph_rgw` (RGW spec, STS, ingress through `/usr/local/sbin/ceph-ingress-apply`, admin user; `rgw_user.yml` is reused by `s3-user.yml` and never takes keys, radosgw-admin generates them), `ceph_cephfs`, `ceph_monitoring` (Prometheus/Alertmanager/Grafana on the `ceph_monitoring` group, node-exporter and ceph-exporter everywhere; bootstrap always skips the monitoring stack so this role owns placement), `ceph_bench` (task files only: `install_fio`, `install_warp`, `rados_mode`, `fio_job`, `report`; used by `bench-*.yml`).

### Ceph-specific rules

- Feature switches in `group_vars/ceph/` (`main.yml`, `rgw.yml`, `bench.yml`; Ansible reads every file of the directory): `ceph_rgw_enabled` (S3 part: `rgw.yml`, alias `s3.yml`), `ceph_rgw_ingress_enabled`, `ceph_rgw_acme_enabled` (derived `ceph_rgw_acme_active` also needs ingress and SSL), `ceph_rgw_sts_enabled`, `ceph_cephfs_enabled`, `ceph_cephfs_mount_nodes`, `ceph_monitoring_enabled`. Gate new tasks on them, including in the hooks.
- `cephfs-mount.yml` pulls all its variables from the admin host (`hostvars[groups['ceph_mons'][0]]`) so it works with any `cephfs_mount_hosts` pattern; keep it that way when editing it.
- `ceph_mons[0]` is the admin host. All cluster commands run there as `cephadm shell -- ceph ...` or `cephadm shell -- radosgw-admin ...`; no Ceph packages are installed on hosts. Spec files are written to `/etc/ceph/specs` and applied with `cephadm shell --mount /etc/ceph/specs -- ceph orch apply -i /mnt/specs/<file>` only when the rendered template changed (or `-e ceph_force_apply=true`).
- Placement is label-based; labels derive from inventory groups via `ceph_host_labels`. Change group membership, not spec files, to move services.
- Idempotency pattern: probe with `--format json` (`failed_when: false`, `changed_when: false`), parse with `from_json`, then act under `when`. Keep new tasks in that style.
- cephadm logs every command line it runs, at debug level, to `/var/log/ceph/cephadm.log` (root-only, `ceph_preflight`), so `no_log` alone does not protect a secret: never put a password or key in a `cephadm shell -- ...` command line. Hand it over as a file under `/etc/ceph/specs` (dashboard password: `ceph dashboard ac-user-set-password -i`; config values: `ceph_config` with `secret: true`, which removes the key and uses `ceph config assimilate-conf -i`, since assimilate-conf never overwrites a set key).
- Only the LVM logical volumes in `ceph_osd_devices` (`/dev/vg_data/lv_data`) are ever given to Ceph. The role classifies them `osd` / `not-lv` / `mounted` / `dirty` / `free`; `not-lv` and `mounted` are always refused, `dirty` unless `ceph_osd_zap_devices=true` (needed once after MicroCeph). Zap uses `cephadm ceph-volume -- lvm zap` without `--destroy`; never `ceph orch device zap`, which would delete the LV. The NVMe PV and the other LVs (`lv_var`, `lv_home`) must never be touched.
- RGW config goes to the `client.rgw` section (`ceph_rgw_config_section`) so it matches every cephadm-named RGW daemon; a change triggers `ceph orch restart rgw.<id>`.
- arm64 quirks, both handled in the roles: cephadm's haproxy/keepalived images are amd64-only (replaced via `mgr/cephadm/container_image_*`, keepalived built locally by `ceph_ingress_image`); Squid's AES-256 CephX keys are unusable by the 5.10 kernel client (CephFS client key is created with `--key_type aes`, which needs `mon_auth_allow_insecure_key` and `aes` in the mon map's `auth_allowed_ciphers`).
- RGW zonegroup `hostnames` must list `ceph_rgw_dns_name` plus every RGW host's short name and FQDN: once the list is set, RGW takes any other Host header as a bucket name. Never set `rgw_dns_name` (the dashboard then connects to that name).
- Benchmarks (`bench-rados.yml`, `bench-s3.yml`, `bench-cephfs.yml`, all via `bench.yml`) take their settings from the admin host through `vars/bench.yml` so any `bench_hosts` pattern works, run each step on all load hosts in lockstep (`include_role` in a loop), clean up their data, and write `bench-results/<timestamp>-<kind>/` on the control node. warp needs `--disable-sha256-payload` against the plain-HTTP RGW endpoints (SigV4 streaming uploads get 403) and a run fails on any warp error.
### k3s-specific rules

- Groups `k3s_servers` (embedded etcd, keep an odd count; the first one bootstraps with `cluster-init` unless another server already holds etcd data, which it then joins) and `k3s_agents`, union `k3s`; settings in `group_vars/k3s.yml`. Servers are not tainted.
- `k3s_node` installs with the vendored official script only when `k3s --version` differs from `k3s_version`; config lives in `/etc/rancher/k3s/config.yaml`. Servers go `serial: 1`. Upgrades go through `subsystems/k3s/upgrade.yml` (`make k3s-upgrade ARGS="-e k3s_version=..."`: pre-flight, drain, install, kubelet version check, exit hooks per node), then the pin in `group_vars/k3s.yml` is bumped.
- Storage: `k3s_ceph` (runs on `ceph_mons[0]`: pool, subvolume group, CSI users with AES-128 keys and ceph-csi's documented caps) publishes facts for `k3s_ceph_csi` (runs on the first server: `HelmChart` manifests in `/var/lib/rancher/k3s/server/manifests/`). Kernel clients on 5.10: msgr v1 monitor addresses, RBD feature `layering`. ceph-csi stays on 3.15.1: 3.16+ ship Tentacle's rbd CLI, which adds `ms_mode=prefer-crc` to kernel maps and the 5.10 kernel rejects it. The node hooks run kubectl on another server; in `command:` tasks quote whole `-o 'jsonpath=...'` arguments (the module strips inner double quotes otherwise).
- Nodes must boot with cgroup v2 (Kubernetes >= 1.35); `cluster/baseline.yml` (tag `cgroup`) edits `/boot/firmware/ubuntuEnv.txt`, a FAT file system, so no Ansible `backup:` there.

### Data platform rules (`subsystems/dataplatform/`)

- Two halves. Ansible (playbooks at the top, roles `dataplatform_*`) bootstraps only what Argo CD cannot own: servicelb node labels and public DNS (`edge`), Argo CD as a k3s HelmChart with the repo and OpenBao seal-key Secrets (`argocd`), OpenBao init/config/generated secrets (`openbao`), the wildcard certificate (`cert`: lego on the first k3s server, deploy hook writes it to OpenBao), RGW users/buckets (`ceph`), and the IAM model (`iam`). Everything else is `gitops/`, laid out like `bigdata-k8s-stack`: `bootstrap/argocd-values.yaml`, `app-of-apps/`, one Application per component in `apps/` with a sync wave, Kustomize directories in `manifests/<layer>/<component>/`, `helm-values/`.
- The gitops files that carry a site value are rendered from their `.in` templates (Settings, above). `make dataplatform-render` checks that every Application points at the repository and revision of `site.yml` and renders every app; run it with syntax-check, lint, configure-check and site-check. Each run writes `.render/report.html` (one self-contained page: the checks, every Application by sync wave with its sources and object kinds, the platform's values, the errors); the CI job `render` keeps it as an artifact, also when it fails. `.ansible-lint` excludes `gitops/`. Ansible never uses `ceph_rgw_endpoint` in the data platform, only `dataplatform_s3_endpoint` (`preflight.yml` asserts they agree); the Ceph-specific IAM (the RGW account, radosgw-admin users, the OIDC provider, AssumeRole by user `trino`) is confined to `dataplatform_ceph` and `dataplatform_iam`, and the roles to Meta Catalog's scripts (`provisioning/lib-iam.sh`) and `dataplatform_iam` (the platform's own).
- Argo CD pulls over SSH with the host keys pinned in `gitops/bootstrap/known_hosts` (`dataplatform_argocd` refuses a server that does not present them; `preflight.yml` checks the Git key against the same file) and the AppProject lists the one repository and the chart sources: a new chart source goes into `gitops/app-of-apps/project.yaml` too.
- No secret in Git, not even encrypted: an `ExternalSecret` per Secret, from OpenBao KV v2 `secret/dataplatform/<namespace>/<name>`, through the namespace's own `SecretStore openbao` (Kubernetes auth role = namespace, policy = its folder only). New generated values go in `dataplatform_openbao_generated` (created once, never replaced); values needed in two namespaces in `dataplatform_openbao_copies`. Argo CD only reads Secrets labelled `app.kubernetes.io/part-of: argocd`. Every ExternalSecret has a `target.template` (at least `engineVersion: v2`). Without one, ESO copies the ExternalSecret's annotations (Argo CD's, `force-sync`) onto the Secret, so each `make dataplatform-sync` rewrote the Secrets, and Stackable restarted Trino on every write.
- iam-sync applies nothing from a Keycloak answer with no group, or without a group it saw earlier in the process (a half-imported realm would revoke everyone); `IAM_SYNC_ALLOW_SHRINK=true` or a restart lets a deliberate removal through. Listings are paged (`first`/`max`).
- The IAM model: one bucket (`dataplatform_bucket`, `s3://dataplatform`), and Meta Catalog is the only place where data access is managed (the user's decision, 2026-10-05; the OpenTofu module, the CI jobs `iam-*`, the `iam-pipeline` CronJob and the merge requests are gone). `gitops/iam/access.yaml` keeps only the platform's part (`bucket`, `admins.groups`, `metacatalog.prefix` and `.provisioner`); a `grants` list fails `files/check_access.py` (`make dataplatform-iam-check`, run by the CI job `ansible`). A member of platform-admins authorizes a lakehouse in Meta Catalog; the script writes each resource's grants into the record, the ConfigMap `governance/metacatalog-grants` (one key per resource, `{path, grants: [{access, users, groups}]}`; Argo CD only creates it: `ignoreDifferences` on `/data`, `Prune=false,Delete=false`; it is `gitops/iam/metacatalog-grants.yaml`, app `governance-iam-access`, wave 1, not Meta Catalog's wave 3: iam-sync applies nothing before it has read it, and Trino (wave 2) needs iam-sync's `trino-iam`, so a fresh install deadlocked with it in wave 3), then converges every role from the whole record (`provisioning/lib-iam.sh`: `curl --aws-sigv4` against RGW's IAM API as the RGW user `metacatalog-iam`, whose user policy allows only role actions on `usr-*`/`grp-*` and denies `dataplatform_iam_platform_roles` (RGW names `UpdateAssumeRolePolicy` `iam:ModifyRoleTrustPolicy` in policies, and lets a non-root account user call `ListRoles` only with the admin capability `roles=read`, `dataplatform_s3_users[].caps`, whatever its policy says); the `Content-Type` header must be set explicitly or RGW refuses the signature; RGW returns documents XML-escaped, never URL-encoded). The generic scrape jobs use `honor_labels: true`; without it, kube-state-metrics' `namespace` becomes the target's. `transform/cluster` sets `cluster="homelab"` only where a metric has no `cluster` label (CloudNativePG and OpenBao have their own). Annotate a new component's pod or Service with `prometheus.io/scrape`/`port`; a pod scraped through its annotation is never scraped again through a Service.
- Logs go to two VictoriaLogs tenants (Grafana data sources "VictoriaLogs" and "VictoriaLogs Stackable").
  - Tenant 1 holds the product logs of every Stackable-managed pod. Each product's Vector agent collects them (`config.logging.enableVectorAgent: true` on every role, plus `vectorAggregatorConfigMapName: vector-aggregator-discovery`; that ConfigMap lives in `compute`). The aggregator's VRL (`helm-values/vector-aggregator-values.yaml`) shapes them into OTLP marked `log.collector=vector`. Its `opentelemetry` sink sends them to the cluster collector, whose `routing/otlp-logs` sends them to tenant 1. Vector's own metrics take the same sink to VictoriaMetrics (`job=vector-aggregator`); it is not scraped.
  - Tenant 0 holds everything else.
  - The agent's `filter/stackable-products` drops Stackable product containers (label `app.kubernetes.io/managed-by` = `*.stackable.tech_*`) except `vector`. So a new Stackable product needs the Vector settings, or its logs disappear.
  - A Stackable container that cannot have a Vector agent (Spark's `spark-submit`: the CRD has no `job.config.logging`) must be routed to tenant 1 by the agent's `routing/stackable` connector instead. The submit script traces its command line with S3 keys, which `transform/stackable-submit` masks, so keep that masking on any new route.
  - Every record carries `log.collector` (`vector`, `otel-agent`, `otel-cluster`).
- Test changes before pushing:
  - VRL: `vector test`.
  - A collector change: `otelcol-contrib validate` on the chart-rendered config, which parses OTTL. The chart renames components (`k8sattributes` -> `k8s_attributes`).
- Grafana dashboards:
  - grafana.com dashboards are pinned by `revision`; without one the chart fetches revision 1. A revision whose uid changed will not replace the old dashboard; see the README's troubleshooting.
  - Our own dashboards are JSON files in `manifests/observability/grafana/dashboards`, loaded by the sidecar (ConfigMap label `grafana_dashboard=1`, folder from the `grafana_folder` annotation). The Logs dashboard's variables use `field:in($var)` with `allValue: "*"`: `in(*)` also matches records without the field, a value list would not.
- JupyterHub (chart `jupyterhub` 4.4.2, namespace `tools`, `helm-values/jupyterhub-values.yaml`, manifests in `manifests/tools/jupyterhub`): GenericOAuthenticator against the Keycloak client `jupyterhub` (`allow_all`, `admin_groups: [platform-admins]`, groups from userinfo; auth state on, `refresh_pre_spawn`, and `hub.extraConfig` hands the login's access token to the server as `KEYCLOAK_TOKEN`: the client carries the audience `trino`, a 12 h token lifespan and is in `dataplatform_iam_client_ids`, so the notebook queries Trino and STS with it), `hub.existingSecret: jupyterhub-hub` (ExternalSecret: `values.yaml` with the client secret, cookie secret and CryptKeeper key as sha256 of OpenBao `tools/jupyterhub`). The chart makes the hub-to-proxy token at render time (`lookup` is empty under Argo CD), so the Application ignores that Secret key and the hub Deployment's `checksum/secret` annotation with `RespectIgnoreDifferences`; never drop that. The hub reads its values from that Secret, so a change of `jupyterhub-values.yaml` needs `kubectl -n tools rollout restart deploy/hub` after the sync. `singleuser.cloudMetadata.blockWithIptables` stays false (privileged init container, refused by Pod Security baseline). The notebook image's jupyterhub must have the hub's major version (chart 4.x = JupyterHub 5): check `docker run --rm --entrypoint python <image> -c 'import jupyterhub; print(jupyterhub.__version__)'` before bumping the tag. Pre-puller, user scheduler and placeholders are off; singleuser egress allows private addresses (S3, Trino, Keycloak).
- Stackable listener class `cluster-internal` only (servicelb would take LoadBalancer Services); every PVC names `storageClassName: ceph-rbd` anyway (`ceph-rbd` is the only default; `k3s_ceph_csi` removes the mark from `local-path`). Charts that generate certificates or secrets at render time cause endless diffs; prefer runtime generation and `ignoreDifferences` on caBundles.

### General

- Everything installed is pinned: `ceph_image` (a full `vX.Y.Z` tag drives `make ceph-upgrade`), the cephadm binary by `ceph_cephadm_sha256`, the keepalived package, `k3s_version`, the vendored k3s installer (`roles/k3s_node/files`), chart versions in `gitops/apps` (the Spark operator's in its kustomization, `manifests/operators/spark-k8s-operator`), container images by tag or digest, collections in `requirements.yml`, the control node's Python tools in `requirements.txt`. Bump a pin on purpose, in its own commit.
- Variables a role defines (`register`, `set_fact`, and the `vars` its callers pass in) start with the role name: `ceph_rgw_user_uid`, `k3s_node_is_server`. ansible-lint enforces it (`var-naming[no-role-prefix]`). Fact names built at runtime must follow it too (`'ceph_bench_' ~ ceph_bench_report ~ '_results'`).
- Jinja pitfall seen here: `some_dict.keys` resolves to the dict method; use `some_dict['keys']` for a field literally named `keys` (radosgw-admin user info).
- STS roles and policies are managed with `radosgw-admin role ...`; OIDC providers need the IAM API, hence `files/oidc_provider.py` (boto3, run on the control node via `delegate_to: localhost` with `ansible_playbook_python`).
- Backups: `ceph_rgw` creates the S3 user `backup` (`ceph_rgw_backup_*`) and its bucket `platform-backups`, keys in `.secrets/s3-backup.json`; k3s reads them for `etcd-s3` (Secret `kube-system/k3s-etcd-snapshot-s3`, `k3s_etcd_s3_*`), `dataplatform_ceph` copies them to OpenBao `governance/backup-s3` for the CloudNativePG `ObjectStore`s (one per cluster, named like it) and the `openbao-snapshot` CronJob (`gitops/manifests/governance/openbao-snapshot`, app in the last wave so that a failed or waiting run blocks no other app; it waits up to 2 h for OpenBao after a power-on; OpenBao role `openbao-snapshot` from `dataplatform_openbao`). The record of grants (`governance/metacatalog-grants`) goes to `metacatalog-grants/` there, hourly, from `iam-reconcile`. The directory (Samba AD) goes to `samba-ad/`, nightly, from the CronJob `samba-ad-backup`. Ceph's own state goes to `backups/ceph/` with `make ceph-backup`. Anything new that holds state gets a backup there and a restore paragraph in its README.
- PostgreSQL backups go through CloudNativePG's Barman Cloud plugin (app `cnpg-barman-cloud-plugin`, wave -3, one replica in `operators`, next to the operator, which finds it by its Service; its link to the operator uses certificates from cert-manager, app `cert-manager`, wave -5, which otherwise only issues the directory's LDAPS certificate). Never `spec.backup.barmanObjectStore` again (CloudNativePG 1.31 removes it): a cluster names its `ObjectStore` (`barmancloud.cnpg.io`, in the cluster's namespace) under `spec.plugins` with `isWALArchiver: true`, its `ScheduledBackup` has `method: plugin`, and retention lives in the `ObjectStore`. The recovery window is in the `ObjectStore`'s `status.serverRecoveryWindow.<cluster>`, no longer in the Cluster's status. While the plugin is down no WAL is archived and no database pod is created. Argo CD's server-side diff cannot switch a live cluster from `barmanObjectStore` to the plugin (the dry run keeps the block written by client-side applies, and the webhook refuses both together): the switch went through `argocd.argoproj.io/compare-options: ServerSideDiff=false` on the Application (only possible per Application), removed afterwards.
- PostgreSQL restores go through `subsystems/dataplatform/pg-restore.yml` (`roles/dataplatform_pg_restore`; `make dataplatform-pg-restore-check`, the drill into a scratch `<cluster>-restore-check`, and `make dataplatform-pg-restore`, which deletes and recreates a cluster). Keep in it: Argo CD paused with `skip-reconcile` on the cluster's Application (from its `tracking-id`) before the delete; the recovery along the live primary's timeline (Keycloak's archive holds an abandoned timeline 2; `latest` fails); `skipEmptyWalArchiveCheck` only until archiving works; the bootstrap patched back to the original `initdb` before Argo CD resumes (CloudNativePG accepts it, the spec then matches Git, so no `ignoreDifferences` is needed); state in `backups/pg-restore/` so a re-run resumes. Clusters are listed in `dataplatform_pg_restore_clusters`, Keycloak last.
- cephadm daemons must not start before the network: `ceph_preflight` installs a `ceph-.service.d` drop-in that waits for an address and a nameserver (RGW once kept an empty resolv.conf, keepalived stayed in FAULT). Keep it.
- Nor before chrony has set the clock: after a power-off the boards boot with the time fake-hwclock saved at shutdown, and chrony steps it hours forward some 25 s later. Under running daemons that step made the monitors mark OSDs down until two shut themselves down, and the placement groups of the others hung in peering. `ceph_preflight` installs and enables `chrony-wait.service` (upstream chrony's unit, `chronyc waitsync`, at most 180 s, `Before=time-sync.target`), which gives meaning to the `After=time-sync.target` of cephadm's units. `post-startup.yml` then waits until every placement group is active and starts an OSD that is down, twice at most (cephadm's units refuse a sixth start within 30 min).
